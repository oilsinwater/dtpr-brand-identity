Primitive Derivation

The construction chain behind every variable × recipe selection in the Form Box, Process Box, and Semantic Box. Why each selection is the right primitive for its recipe — recovered through a reverse strip-down of the existing corpus.

How to read this page

This page documents the upstream construction chain behind every parameter selection in the three morphological boxes (§14 Form, §15 Process, §16 Semantic). The boxes present parameters; they do not derive them. This page recovers the missing derivation layer — the five-step reasoning chain that justifies why each recipe picks the option it picks.

Each of the 18 variables has three sub-derivations, one per canonical recipe (Regulatory / Maker / Commons, per §17). Each sub-derivation follows the same five-step chain: Inventory → Constraint extraction → Collision / picturability test → Geometry / scale / rendering test → Primitive confirmation. Where corpus evidence is thin, it is flagged. Where an open question from brand memo §9 affects a variable, it is linked inline.

What this page is not: not a brand book, not a parameter presentation (that's §14–§16), not a recipe selector (that's §17). It is the reasoning layer underneath all three.

Form Box Derivations (§14)

Form Variable 1: Shape Primitive

Regulatory recipe — selection: D Hexagon Grid

1. Inventory

The canonical DTPR mark (§06 Marks) is a flat-top hexagon containing an inner circle (r=8 at center 14,16) and an offset square (7×8 at position 10,12). Three variants exist: blue solid (#002684), black solid, outline (1.5px stroke). Sketch metadata names it dtpr_icons/container/hexagon — deliberately a container, not a logo. §18 Blueprint specifies R=100 master unit, R=45mm for signage.

2. Constraint extraction

Regulatory recipe needs ISO 3864 co-existence: the shape must not collide with ISO warning triangles or mandatory circles, and must be recognizable at 10m viewing distance.

3. Collision / picturability test

The hexagon passes the ISO collision test — ISO 3864 uses triangles (warning), circles (mandatory), squares (optional); the hexagon reads as none. The isometric 3D hex (Posture B) fails — extrusion is illegible at signage scale. The wireframe network (Posture C) fails — thin lines vanish at R=45mm print.

4. Geometry / scale / rendering test

§18 geometry: width=2R=90mm, height=R√3≈77.9mm, stroke=R×0.02=0.9mm at signage scale. Flat-top tessellates with row_offset=R√3/2. Inner circle and offset square strip away at 16px render without losing identity.

5. Primitive confirmation

The flat-top hexagon is the shape primitive for the Regulatory recipe because it is the only candidate that passes the ISO 3864 collision test while maintaining geometric consistency with the signage blueprint.

Maker recipe — selection: B Graph Paper

1. Inventory

MakeShift 2026 (§04) uses graph-paper texture as background field for all formats. vision.dtpr.io (§03) uses the same. Brand memo §5: 'Graph-paper / grid maker aesthetic — confirming the vision.dtpr.io baseline.'

2. Constraint extraction

Maker recipe serves developers needing a 'hackable-by-design' register. Shape must signal builder/integrator context at desktop viewport sizes.

3. Collision / picturability test

Graph-paper square passes picturability for developers — 'graph paper = blueprint = build here.' Flat hexagon reads as deployed-output, not builder-input. Rounded hex reads as consumer UI.

4. Geometry / scale / rendering test

Square format maps to CSS grid: background repeating-linear-gradient at 8px intervals. Doesn't require hex tiling math. Accepts both hexagon (as icon container) and square (as layout field) as co-existing primitives.

5. Primitive confirmation

The graph-paper square is the shape primitive for the Maker recipe because it signals builder context that the hexagon (deployed output) cannot.

Commons recipe — selection: C Organic + Hex

1. Inventory

§10 Illustrations shows human-centered scenarios with rounded forms on hexagonal containers. §09 Iconography uses hex as container with organic pictographic content (people, hands, buildings).

2. Constraint extraction

4. Geometry / scale / rendering test

5. Primitive confirmation

Form Variable 2: Grid Tiling

Regulatory recipe — selection: D ISO Modular

1. Inventory

§18 Blueprint: honeycomb tiling, flat-top hexes, col_step=2R+gap, row_step=R√3, odd_offset=col_step/2. At R=45mm: gap=3.6mm, col_step=93.6mm.

2. Constraint extraction

Physical signage needs deterministic grid behavior: no shift between print runs, predictable tessellation on mounting hardware.

3. Collision / picturability test

Honeycomb and ISO modular both pass tessellation. Sparse network fails — variable spacing breaks print determinism. Linear grid fails – abandons hexagonal primitive.

4. Geometry / scale / rendering test

§18 math: gap=R×0.08=3.6mm, row_offset=R√3/2. 'Strict ISO' = grid never breaks, no responsive reflow.

5. Primitive confirmation

The ISO modular honeycomb is the grid primitive for the Regulatory recipe because it maintains deterministic print behavior while preserving the hexagonal primitive.

5. Primitive confirmation

The Safety Semantic palette is the color primitive for the Regulatory recipe because it achieves ISO 3864 co-existence while maintaining brand recognizability.

Form Variable 6: Motion Behavior

Regulatory recipe — selection: A None / Static

⚠ Thin corpus evidence — no motion principles are documented (brand memo §9.9: 'Motion principles. None exist.'). This derivation is constructed from absence.

1. Inventory

No motion principles are documented anywhere in the DTPR corpus. Brand memo §9.9: 'Motion principles. None exist.' The absence is the evidence — physical signage is inherently static.

2. Constraint extraction

Regulatory recipe targets physical signage panels. Printed/static surfaces cannot animate. Motion is structurally impossible in this deployment context.

5. Primitive confirmation

The absence of motion is the motion primitive for the Regulatory recipe because the physical signage medium structurally forbids it.

Process Variable 1: Grid Decomposition

Regulatory recipe — selection: D Strict ISO

1. Inventory

§18 Blueprint specifies honeycomb tiling math. 'Strict ISO' means the grid never breaks — no decomposition, no reflow, no responsive splitting.

2. Constraint extraction

Physical signage requires deterministic grid behavior: panel layout is printed once and mounted. No decomposition is possible or desirable.

3. Collision / picturability test

Strict ISO passes — enforces grid integrity by refusing decomposition. Concentric rings fail — nesting inward is decorative, not structural. Triangular shards fail — destroys container primitive.

4. Geometry / scale / rendering test

§18: grid locked at gap=R×0.08, col_step=2R+gap. No responsive breakpoints apply. CSS grid-template is fixed.

5. Primitive confirmation

Strict ISO is the grid decomposition primitive for the Regulatory recipe because it refuses decomposition — the grid is fundamental structural, not decorative.

Source citations
  • §18 Blueprint
  • §21 Responsive

Maker recipe — selection: B Fluid Overlay

1. Inventory

§21 Responsive spec defines breakpoints at 320px, 768px, 1024px, 1280px. Fluid Overlay means the grid reflows at each breakpoint.

2. Constraint extraction

Developer portals need responsive grid behavior: code blocks, sidebars, and content areas reflow across viewport sizes.

3. Collision / picturability test

Fluid Overlay passes — CSS Grid auto-fit/minmax allows column reflow. Halves & Thirds fail — fixed divisions don't reflow. Centroid Explosion fails — radial doesn't map to rectangular viewports.

4. Geometry / scale / rendering test

CSS Grid: repeat(auto-fit, minmax(280px, 1fr)). <768px: 1 column. 768–1024px: 2 columns. ≥1024px: 3 columns.

5. Primitive confirmation

Fluid Overlay is the grid decomposition primitive for the Maker recipe because it allows responsive reflow while maintaining the graph-paper grid aesthetic.

Process Variable 2: Scale Adaptation

Regulatory recipe — selection: D Physical Distance

⚠ Thin corpus evidence — the physical-distance zones (10m/2m/0.5m) exist in §21 spec but deployment evidence validating these thresholds is limited.

1. Inventory

§18 Blueprint defines R=45mm for physical signage with 0.5m minimum viewing distance. §21 specifies three distance zones: 10m (wayfinding), 2m (reading), 0.5m (touch/QR scan).

2. Constraint extraction

Physical signage scale adaptation must respond to viewing distance, not viewport width. Same panel must be legible at 10m, 2m, and 0.5m.

3. Collision / picturability test

Physical Distance passes — ties scale to human physical interaction. Elastic Squeeze fails — aspect ratio distortion illegible. Detail Reduction complements but isn't primary.

4. Geometry / scale / rendering test

Three zones: 10m → icon-only (R=45mm visible at distance); 2m → icon + label (text readable); 0.5m → full detail including QR code.

5. Primitive confirmation

Physical Distance is the scale adaptation primitive for the Regulatory recipe because it grounds scale in the human body's relationship to physical signage.
